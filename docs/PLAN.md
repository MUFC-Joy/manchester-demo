> 目标：复刻参考视频的形式感（方块城市 + 相机叙事 + 彩蛋），但基于**真实地理位置**：  
> 曼彻斯特全城街区 + 两座球场（老特拉福德 / 伊蒂哈德）放在真实坐标上，跑在浏览器里。

## 1. 目标拆解：你到底在复刻视频的什么

先想清楚参考视频的感染力来自哪三件事，再动手：

1. **形式感**：方块/体素风格，低多边形，色彩明快 —— 这不是技术妥协，是**美术选择**，它同时解决了"真实城市太贵做不动"的问题。
2. **叙事**：镜头有一场演出（飞行路线、停靠点、庆祝时刻），不是让人自己瞎转。
3. **彩蛋**：结尾的惊喜，是发到 B 站能被刷弹幕的点。

**由此推出三条设计约束：**

- 我们做的是"真实地理 + 方块风格"，不是写实 —— 所以写实级球场模型（18 万面）反而是负担；
- 相机飞行路线（camera tour）是**一等公民**，第 4 阶段专门做；
- 彩蛋要在 MVP 里就留好钩子，不是最后想。

**MVP 定义（先说清楚不做什么）：**

- ✅ 做：曼城市区真实街区（建筑/道路/河运/铁路/绿地）方块化、两座球场正确位置与正确朝向、一键飞行 Tour、昼夜切换、1 个彩蛋、部署上线。
- ❌ 不做（v1）：经济系统、商店、铁路运营玩法（CubeCity 那套思路）、室内看台选座、多人、声音系统（可后置）。扩展玩法与氛围（人流/车流/电车/地标/上帝视角/夜幕序列等）的分级提案见《manchester-demo-玩法与氛围扩展.md》，进 v1.5/v2。

## 3. 总体架构与数据流

```
┌─────────────── 离线阶段（构建时，跑一次） ───────────────┐
│                                                        │
│  Overpass API ──► scripts/fetch-osm.mjs ──► 原始JSON    │
│  (建筑/道路/铁路/水/绿地, 分片请求+重试)      │          │
│                                            ▼           │
│                              scripts/build-city-json.mjs│
│                       (简化轮廓、高度量化、坐标投影、瘦身) │
│                                            │           │
└────────────────────────────────────────────┼───────────┘
                                             ▼
                              src/data/city.json  (几百KB~几MB, 进Git)
                                             │
┌────────────────── 在线阶段（浏览器） ────────▼───────────┐
│                                                        │
│  city.json ──► city/ 三环LOD生成 ◄── core/geo.js 投影    │
│  stadiums/ 程序化球场(OT复用MIT代码, Etihad自写)          │
│  camera/tour.js 飞行叙事   ui/ HUD+昼夜   egg/ 彩蛋      │
│                                                        │
│                 ▼                                       │
│        Vite 打包 ──► GitHub Pages 静态部署               │
└────────────────────────────────────────────────────────┘
```

设计要点：

- **数据在构建时取好、瘦身、进 Git**。运行时不依赖 Overpass（否则限流/超时直接杀死演示）。
- **两座球场都是代码生成**（参数化：碗形看台 + 悬挑屋顶 + 草坪 canvas 贴图），和城市方块风共享同一套材质与色板 —— 风格统一是白送的。
- 唯一的外部二进制资产是**零**。整个项目没有版权灰区（除 OSM 署名义务，见 §6.9）。

## 5. 分阶段实施计划

每阶段四件事：做什么 / 怎么做 / 怎么用 AI / 验收标准。**每个阶段结束时 Git 打一个 tag。**

### P0 · 环境与学习准备（半天）

- 装 Node 20+、Git、Blender 4.x（P3 才用，可后置）；注册 GitHub。
- 学三样东西，各 1 小时：[overpass-turbo.eu](https://overpass-turbo.eu)（在地图上跑查询、可视化结果，学 OSM 数据长什么样）、Three.js 官方 [InstancedMesh 示例](https://threejs.org/examples/)、`git tag`。
- 建 `docs/WORKLOG.md`，从此每次开工先写一段：目标/做了什么/卡在哪。

**验收**：`npm create vite` 起的空项目能在浏览器显示一个旋转的立方体。

### P1 · 最小垂直切片（第 1 个周末，~8h）⚠️ 全项目最重要的一步

**目的：用最小代价同时验证"数据管线"和"渲染管线"两条腿。**

- 取老特拉福德周边 **1km²**（`bbox=53.458,-2.297,53.468,-2.285`）的建筑数据；
- 写 `fetch-osm.mjs` 拉取 → `build-city-json.mjs` 投影到米制局部坐标；
- Three.js 里把每栋楼按真实 footprint **挤出**（extrude），平面落在地上；
- OrbitControls 环绕。

**怎么用 AI**：把 Overpass QL 交给 AI 生成，但**必须先在 overpass-turbo 里人工跑一遍**看结果对不对，再进管线。挤出几何有三角形绕序/法线问题，把报错全文贴给 AI。

**验收**：浏览器里能认出老特拉福德周边的真实街区形状（对照卫星图）。  
**会踩的坑**：OSM 的 `way` 闭合多边形首尾点重复要去重；经纬度先后顺序（lat, lon）写反是最常见低级错误；挤出方向用了 +Y 而你的"地面"是 XZ 平面。

### P2 · 全域城市 + 地理配准（第 2 个周末，~10h）

- bbox 扩到全域 `53.44,-2.33,53.51,-2.13`（约 7.8km × 13.3km，覆盖索尔福德码头—市中心—伊蒂哈德），**分片请求**（比如 3×3）避免 Overpass 超时；
- **三环 LOD**（细节见 §6.2）；
- 道路/铁路/水/绿地各自成层（运河和 Ship Canal 是识别曼城的标志性水系，必须做）；
- **两座球场先用占位盒**（红色/蓝色 180m 长的盒子）放在真实坐标上；
- 加一个**开发期底图校准层**：把 OSM 栅瓦片铺在地面上，半透明，肉眼校对城市层与底图是否对齐，验收后隐藏。

**怎么用 AI**：让 AI 写分片+重试逻辑；把 InstancedMesh 性能问题拿去问；**让 AI 反驳你的 LOD 划分**（"这是我按距两球场距离分的三环，找出不合理处"）。

**验收**：①俯瞰能认出曼彻斯特市区轮廓与两条运河；②占位盒位置与卫星图误差目测 < 30m；③中端核显笔记本 60fps。  
**会踩的坑**：全量建筑一次 `mergeGeometries` 会把内存打爆 —— 按瓦片分块合并；Overpass 单次请求建议 ≤ 1 个瓦片，429 就退避重试；很多建筑没有 `height`/`building:levels` 标签，需要默认值策略（住宅 8m、市中心随机 15–40m，反正要量化成方块阶梯，缺失不可耻）。

### P3 · 球场资产（第 3 个周末，~10h）

- **老特拉福德**：读 stadium-seat-explorer 源码，抽出其 OT 的生成模块（看台碗、座位、屋顶），接进我们的材质系统，换成方块风色板。**保留其 MIT 版权头注释。**
- **伊蒂哈德**：自写参数化生成 —— 伊蒂哈德形体比 OT 简单（圆角矩形碗 + 南看台单层大顶 + 索网屋顶意象）。给 5 个参数：长、宽、看台层数、屋顶悬挑、朝向。Sketchfab 的 PeeJaa 模型打开转着看，**只当外形参考**，不下载使用。
- 草坪：canvas 程序化条纹贴图 + 中圈/禁区白线，一个 512×1024 canvas 搞定，比找贴图快且无版权。
- Blender 在本阶段的唯一用途：**学习工具** —— 如果你觉得代码里的碗形不对劲，用 Blender 造一遍找感觉；或将来真要处理外部 GLB 时用（AI 写 bpy 脚本，见 §9 模板 2）。

**怎么用 AI**：把 stadium-seat-explorer 的相关源码贴给 AI 要求讲解结构；让它给你生成 Etihad 碗形几何的数学（圆角矩形放样）；生成的几何**永远先在 Blender 或 three.js editor 里目检**再进项目。

**验收**：两座球场可环绕无穿模，屋顶/看台/草坪完整，每座 ≤ 8 万面，和城市放一起风格不违和。  
**会踩的坑**：球场默认朝向和真实朝向不一致（见 §6.1 朝向校准）；模型原点不在球场中心导致放置偏移；外观太"干净"反而不像球场 —— 加看台座椅的彩色 instanced 小方块（OT 红色座椅海、Etihad 蓝色），效果炸裂成本极低。

### P4 · 相机叙事 + 昼夜 + UI（第 4 个周末，~10h）

- **先写分镜再写代码**（一页纸）：
  1. 高空开场，缓缓压向城市天际线 →
  2. 沿 Ship Canal 飞向老特拉福德，绕场一周（红色座椅海）→
  3. 沿 Metrolink 线穿过市中心 →
  4. 抵达伊蒂哈德，绕场一周（蓝色）→
  5. 拉升至全城鸟瞰，两座球场上空分别亮起"传奇墙"：老特拉福德点亮曼联传奇、伊蒂哈德点亮曼城传奇（名单见附录 D），收尾字幕 "THIS IS MANCHESTER"。
- `CatmullRomCurve3` 定义路径，`getPointAt(t)` 驱动相机，每段配时长与缓动；UI 提供"自由视角 / 一键 Tour"切换。
- 昼夜：白天方向光 + 天空色；夜晚切换 —— 城市窗户用**预先生成的 emissive instanced 面片**（不是真点光源），球场四角"灯塔"用发光材质 + 简单辉光贴图，不做后处理 Bloom（省性能）。
- UI 按 `DESIGN.md` token 落地：左上角标题 `MANCHESTER · THEATRE OF DREAMS`，底部球场切换 + Tour 按钮，右上昼夜开关，左下图例（红=OT，蓝=Etihad）。

**怎么用 AI**：分镜先让 AI 批一轮（"这条路线无聊在哪"）；曲线缓动函数让它写；DESIGN.md 写好后直接连同 hud.js 现状一起丢给 AI 改样式。

**验收**：一键 Tour 全程丝滑 60fps，昼夜切换不闪帧，UI 在 1366×768 和手机竖屏都不崩。

### P5 · 彩蛋 + 性能 + 上线（第 5 个周末，~6h）

- 彩蛋（选两个，键盘触发，实现都极便宜）：
  - 任意时刻键入 **1999** → 老特拉福德上空升起金色奖杯 sprite + 底部字幕 "补时 3 分钟，诺坎普之夜"；
  - 键入 **1000** → 全城红蓝双色烟花（instanced 粒子）+ 两座球场大屏分别滚动曼联/曼城传奇名录（附录 D）。
- 性能收尾：`renderer.setPixelRatio(Math.min(devicePixelRatio, 2))`、雾收远景、加画质切换（移动端自动降 LOD）、stats 面板移除。
- 署名页/角标：`© OpenStreetMap contributors`（ODbL 义务）+ "非官方粉丝作品，与曼联/曼城俱乐部无关" + 代码来源致谢。
- 部署 GitHub Pages（Actions 里 `vite build` → push `dist/`），手机实测一遍。

## 6. 细节问题逐个细说

### 6.1 坐标系统与地理配准（最容易翻车的地方）

- 全项目用**局部平面坐标（米）**，不用经纬度渲染。以两球场连线中点为原点：

```js
// core/geo.js
export const LAT0 = 53.4731, LON0 = -2.2459;          // 两球场中点
const M_LAT = 111320;
const M_LON = 111320 * Math.cos(LAT0 * Math.PI / 180); // ≈ 66270 m/deg

export function ll2xy(lat, lon) {
  return { x: (lon - LON0) * M_LON,
           z: -(lat - LAT0) * M_LAT };  // 北为 -z，屏幕上方
}
// 老特拉福德 (53.4631, -2.2913) → x≈-3009, z≈+1113
// 伊蒂哈德     (53.4831, -2.2004) → x≈+3015, z≈-1113
// 两场直线距离 ≈ 6.4 km —— 放好后量一下,对不上就是配准错了
```

- 城市尺度下这个简化投影误差可忽略（纬度变化 0.08°，cos 项漂移 < 0.1%），**不要上 Web Mercator 或地理坐标系库**，徒增复杂度。
- **朝向校准**：球场的 yaw 角和地图对不上会立刻穿帮。方法：开发期把半透明 OSM 卫星瓦片铺在地面（P2 的校准层），把球场模型转到位后**读出 yaw 角写死成常量**，然后隐藏瓦片。老特拉福德和伊蒂哈德的长轴都不是正南北，必须实测。
- **坐标约定一次性定死**：Three.js 是 Y-up，模型若来自 Z-up 来源（如 Blender 默认）要转；全项目只在 `geo.js` 一处做换向，其他代码只面对"XZ 地面 + Y 高度"。


### 6.2 性能预算与三环 LOD

总预算：**全场景 ≤ 60 万三角面、≤ 200 draw calls、桌面 60fps / 手机 30fps**。

| 环   | 范围           | 表现                                 | 实现                                             |
| --- | ------------ | ---------------------------------- | ---------------------------------------------- |
| A 环 | 每球场半径 600m   | 按真实 footprint 挤出 + 高度阶梯（方块感）       | `ExtrudeGeometry` + 按 GPU 分块 `mergeGeometries` |
| B 环 | 两场连线走廊 + 市中心 | 简化 footprint，InstancedMesh 单位盒按楼缩放 | **1 个 InstancedMesh ≈ 1 个 draw call 画几万栋**     |
| C 环 | 其余           | 只保留主干路网 + 大体量建筑剪影                  | 合并平面 + 少量大盒                                    |

- 配色和材质全局共享（`core/materials.js`），`MeshLambertMaterial` 足够（方块风不需要 PBR），**关闭全场景阴影**；只给球场区开一个 100m 见方的 shadow camera（阴影范围小才不糊）。伪 AO：建筑底部顶点色压暗即可。
- 雾（`FogExp2`）是免费的性能工具：收掉远细节还给画面加了"氛围"。

### 6.3 数据预取与瘦身

- Overpass 公共实例有限流与并发限制。纪律：**分片（≤ 3km 边长）、串行 + 429 退避重试、超时 180s、结果立刻落盘**。
- 用 `out geom;`（几何内联在 way 里）而不是 `(._;>;); out body;`，解析简单、体积小。
- `build-city-json.mjs` 做四件事：① Douglas-Peucker 简化轮廓（容差 1.5m，方块风允许粗暴）；② 高度量化到 4m 阶梯（风格 + 省面）；③ ll2xy 投影 + 转成紧凑结构（Float32 数组化的 footprint）；④ 输出单文件 `city.json`。预期全域 4–8 万栋 → JSON 约 3–8MB，gzip 后 1–2MB，完全可进 Git。
- **全城建筑量级提醒**：曼彻斯特市区这个 bbox 里建筑可能到 6–8 万栋。B/C 环必须有丢弃规则（footprint < 40m² 的 C 环直接不画），别硬扛。

### 6.4 风格统一（决定成片质感的隐形关卡）

方块感的来源是三个量化参数，**做成常量集中管理**：网格吸附 2–4m、高度阶梯 4m、色板 ≤ 8 色。

- 色板建议：地面 `#3a4a3f`（偏灰绿）、路 `#2b2f36`、水 `#274a63`、建筑主体 2–3 个暖灰、A 环屋顶给少量赤陶红点缀、球场区外圈草地提亮。夜景统一压蓝 + 窗光暖黄。
- **一致性检查**：P3 结束时截一张两球场 + 周边街区的同框图，和参考视频逐项对比（色调/密度/轮廓复杂度）。风格断裂在这里暴露，别等录屏那天。

### 6.5 草坪与看台的程序化细节

- 草坪：`CanvasTexture` 画 12 条深浅绿条纹 + 白线（边线/中圈/禁区/点球点），`anisotropy=8`。成本几乎为零，观感提升最大的一笔。
- 座椅海：每球场 ~5 万座位 = 5 万个 instanced 2cm 小方块？不 —— 用**合并的 InstancedMesh 按看台分段生成**（每段几千 instance），OT 全红、Etihad 全蓝。远处看是"色海"，近看有颗粒感，这正是参考视频那种味道。
- 屋顶：OT 用悬挑环梁意象（四个独立大顶 + 角部开口），Etihad 用南看台单侧大顶 + 索网线条（`LineSegments` 画几根索，象征即可）。

### 6.6 昼夜系统

- 用两套预烘焙状态切换（lerp 过渡 2s），**不要做实时太阳系统**：`light.intensity`、天空色、雾色、建筑窗户 emissive 开关、球场灯塔开关，全部插值。夜景的城市窗光是"伪的"—— 每栋 B 环楼顶随机贴 1–3 个发光小面片，全城合计 ~10 万 instance，一个 draw call。

### 6.7 相机叙事工程细节

- Tour 本质是：`CatmullRomCurve3` 位置曲线 + 每段 lookAt 目标插值 + 时长表。三样都做成**数据表**（数组常量），改分镜只改表不改代码。
- 自由视角用 OrbitControls 时把 `minDistance=80, maxDistance=15000, maxPolarAngle=88°` 锁死，防止钻进楼里和翻到地下。
- Tour 播放时用户拖动鼠标 = 立刻中断 Tour 进自由视角（别跟用户抢相机）。

### 6.8 移动端

- 判定 `isMobile` → C 环直接清空、pixelRatio 限 1.5、关阴影。这个项目 90% 的观看会发生在微信/B 站内嵌浏览器里，**移动端不是可选项**。

## 9. 如何用 AI 做这个项目（方法论 + 可复制 Prompt 模板）

### 9.1 五条纪律（本方案 §2 的三处翻车就是反例）

1. **验证一切外部引用**：AI 给的仓库名/能力/授权，人肉点开链接确认后才允许进入计划。把这条写进你的 WORKLOG 模板。
2. **小步闭环**：每次让 AI 产出的东西必须能立刻运行/渲染/看到结果。禁止"先让 AI 生成 500 行完整项目"——出了错你不知道哪一层错了。
3. **给上下文的姿势**：贴**完整报错** + 相关代码片段 + 版本号（Three r180、Blender 4.x），而不是"报错了怎么办"。Blender/Three 生态版本差异大，AI 需要版本才能给对 API。
4. **让 AI 当审稿人而不只是写手**：每阶段收尾让它攻击你的方案（模板 5）。你在上一轮对话里其实已经在用这个模式（"你对方案的反驳的点"），这是对的习惯，保持。
5. **会话记忆外置**：`WORKLOG.md`（做了什么/卡在哪/下一步）+ `DECISIONS.md`（定了什么不再讨论）。每次新 AI 会话开头贴这两个文件，任何会话都能无缝接力。AI 会话开场白模板与文档串联规则见《manchester-demo-实施手册.md》§1。

### 9.2 六个可直接复制的 Prompt 模板

1. **Overpass 查询**："我要 bbox 53.458,-2.297,53.468,-2.285 内的建筑（含 building:levels/height 标签）、道路、水系。给我 Overpass QL，用 `out geom;`。我会先在 overpass-turbo.eu 人工验证。"
2. **bpy 脚本**："Blender 4.x，写一段 bpy 脚本：选中物体，原点设到包围盒底面中心，应用缩放，Z-up 转 Y-up，导出 glb。每步加注释说明为什么。"
3. **Three.js 最小复现**："写一个**单 HTML 文件**（importmap 引 three@0.180），只做一件事：X。不要任何其他功能 —— 我要先理解再集成。"
4. **代码审查**："这段 footprint 挤出代码，三角形绕序和法线方向对吗？Y-up 下地面是 XZ 平面。指出具体行。"
5. **方案攻击**："这是我的 LOD 三环划分（贴表）。以 60fps、6 万栋建筑为约束，列出这个划分最可能失败的 3 个场景和修法。"
6. **概念学习**："用大一新生能懂的话解释 InstancedMesh 为什么省 draw call，配一个 three.js 十行例子。"

### 9.3 学习路线内嵌说明（你学到的不是"做完了"，是这五样）

- **P1** 学：地理数据管线（OSM/Overpass/GeoJSON）、坐标投影直觉；
- **P2** 学：性能工程（LOD/instancing/draw call 预算）——这是 3D 开发里最通用的硬技能；
- **P3** 学：程序化建模（参数化几何）+ 一点 Blender；
- **P4** 学：相机数学（曲线/插值/缓动）+ 设计系统落地；
- **P5** 学：部署与发布闭环 + 录屏叙事。  
  比"Blender 修补模型"值得学得多 —— 前者可迁移到任何 3D/数据项目，后者是一次性手艺。

1. **时间预算**：业余时间 5–6 个周末，约 45–60 小时。其中 P1+P2 占 40%——值得，因为它们杀死最大风险。

### B. 高度默认值与量化策略（`build-city-json.mjs` 内）

```js
function quantizeHeight(tags, footprintArea) {
  const h = tags["height"] ? parseFloat(tags["height"])
        : tags["building:levels"] ? parseFloat(tags["building:levels"]) * 3.2
        : footprintArea > 2000 ? 15 + Math.random() * 25   // 大体量默认
        : 6 + Math.random() * 9;                            // 住宅默认
  return Math.max(4, Math.round(h / 4) * 4);                // 4m 阶梯
}
```

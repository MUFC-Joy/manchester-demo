## 一、项目是什么

一个**基于真实地理数据的曼彻斯特 3D 方块城市演示**（Three.js + Vite）：

- 全城 **61,800 栋建筑**、道路网、铁路、运河、绿地，全部来自 OpenStreetMap 实测数据
- **两座程序化生成的真实球场**：老特拉福德（红色座椅海，4,946 座）与伊蒂哈德（蓝色座椅海，4,304 座），按真实坐标、真实朝向、真实尺寸放置
- **78 秒 6 章节飞行相机 Tour**，用户拖动即中断
- **昼夜切换**：2 秒渐变 + 全城暖黄窗光
- **两个数字彩蛋**：键盘敲 `1999` 升起金色奖杯（致敬曼联三冠王）；敲 `1000` 全城红蓝烟花 + 双雄传奇墙（致敬曼城百分王朝）
- **运行时零网络依赖**：数据全部在构建期取好、瘦身、打包

## 四、踩过的 Bug 全记录（现象 → 根因 → 修复）

### Bug-1：`building=stadium` 陷阱 ⭐ 最隐蔽

- **现象**：老特拉福德的红色座椅海"永远看不见"。改颜色、改灯光、改屋顶悬挑、正俯视拍摄——全部无效，座椅红占比始终 0.01%。
- **排查过程**：强制把座椅顶点改成亮青色做决定性实验，青色依然不出现 → 结论是"被别的东西盖住了"，而不是"没渲染"。
- **根因**：OSM 里老特拉福德的四个看台（Sir Alex Ferguson Stand 等）被标为**四个独立的 `building=stadium` way**。分类函数把它们当普通建筑挤出成 30 m 高的实心体，**正好整体盖住程序化球场**。
- **修复**：`classify()` 中显式排除 `building === 'stadium'`。建筑数 233 → 229，座椅红立即可见。
- **通用教训**：当"改什么都没反应"时，优先怀疑**遮挡**而不是渲染；用改色实验区分"没画"和"被盖"。

### Bug-2：InstancedMesh 视锥剔除错误

- **现象**：4,946 个座椅实例一个都不可见，三角形数比预期少了整整座椅那一份。
- **根因**：InstancedMesh 默认按**单个实例几何（0.62 m 小盒子）的包围球**做视锥剔除，而整个球场远离场景原点，包围球永远在视锥外 → 整块剔除。
- **修复**：`inst.frustumCulled = false`。
- **通用教训**：所有"实例放在远离原点处"的 InstancedMesh 都必须关掉视锥剔除或手动设置正确的包围球。

### Bug-3：多边形质心公式分母错误

- **现象**：153/233 栋建筑被 LOD 分环逻辑"错杀"（分配到错误环甚至丢弃）。
- **根因**：鞋带公式求质心时，分母用了**无符号面积**的 6 倍但符号处理错误，导致环向多边形的质心坐标算到了错误位置。
- **修复**：重写 `centroidAndArea()`，用带符号面积正确归一。
- **通用教训**：鞋带公式的符号约定要在代码里写注释并做单测。

### Bug-4：夜景窗光埋在实心几何体内部

- **现象**：夜景切换后暖黄窗光像素为 0。
- **根因**：窗光平面片随机放在"0.45~0.95 倍楼高处"，但建筑是**实心挤出体**，这些位置全在楼体内部，被外壁遮挡。第一次修复改成水平朝上的平面片后又因为低机位侧对相机而几乎不可见。
- **修复**：窗光改为**小方块**（任意角度可见）并放到**楼顶上方**。窗光像素 0 → 64 → 放大后 806，夜景氛围达标。
- **通用教训**：向实心体内部添加发光元素必然被遮挡；窗光类装饰要么贴外壁要么置顶。

### Bug-5：Tour 时间单位不匹配

- **现象**：点击一键 Tour，相机瞬间飞完全程。
- **根因**：主循环把 `requestAnimationFrame` 的 dt（**毫秒**）直接传给 `tour.update()`，而模块内 `TOUR_DURATION` 是**秒**，t 一次性加到 205。
- **修复**：统一为秒。
- **通用教训**：跨模块的时间参数在接口注释里写明单位。

### Bug-6：glTF 根节点旋转无效（Blender 阶段，附带记录）

- **现象**：给椅子根节点设 `rotation_euler[2] = 180°`，打印值正确但模型纹丝不动。
- **根因**：glTF 导入的节点 `rotation_mode = QUATERNION`，euler 通道被完全忽略。
- **修复**：先 `rotation_mode = 'XYZ'` 再设欧拉角。

### Bug-7：材质/曝光连环误判（Blender 阶段，附带记录）

- **现象**：椅子材质怎么调都"发浅"，纯黑基色都渲染成浅褐。
- **根因**：Poly Haven HDRI 按物理亮度标定，strength=1.0 下场景过曝数档；同时预览图的显示增强会**把暗图提亮**，导致肉眼判断系统性失真。
- **修复**：**放弃看图，改为读像素定量判断**。曝光扫描定出最佳世界光强 0.14，椅子实测像素 (0.216, 0.137, 0.051) 稳定为深胡桃木。
- **通用教训**（本项目最重要的方法论收获）：**3D 验收永远不要靠看图**。预览有显示增强、tone mapping、曝光补偿；用像素采样 + 数值断言做验收，问题一次定位。

### Bug-8：数据加载导致的包体问题（部署阶段）

- **现象**：`vite build` 产物 6.9 MB——city.json 被 Vite 内联进 JS bundle。
- **风险**：手机端 JS 解析与首屏时间显著变差。
- **修复**：city.json 移到 `public/data/` 运行时 `fetch` 并行加载。JS 包体 6.9 MB → **615 KB**。

## 五、风险清单与应对方案

### 风险-1：OSM 数据质量与时效

- **风险**：OSM 是众包数据，建筑高度常缺失（目前用"层数 → 4 m 量化 → 缺失则按面积估"的降级链）；个别建筑轮廓错误；数据随社区更新而变化。
- **应对（已做）**：高度三段降级链；轮廓 DP 简化 1.5 m 消除噪点；数据快照进仓库，**结果可复现**。
- **应对（可选）**：需要更精确高度时接入 Microsoft Building Footprints 或 Ordnance Survey 开放数据；数据更新只需重跑 `fetch-osm.mjs full && build-city-json.mjs full`。

### 风险-2：Overpass API 可用性

- **风险**：主站过载（本次实际遇到 504 / 429 / 406 多次）；未来某次抓取可能长时间失败。
- **应对（已做）**：多镜像回退（kumi.systems / osm.ch 等）+ 429 指数退避 + 分片断点续传。
- **应对（可选）**：日常无需再抓——**city.json 已进 Git，数据生命周期内不再依赖 Overpass**；只有换城市或扩范围才需要网络。

### 风险-3：性能（低端设备 / 手机）

- **现状**：桌面端 518 k 三角形 / 28 draw calls 余量充足；但手机 GPU 与内存差异大，未实测。
- **应对（已做）**：三环 LOD + C 环丢弃规则已把全城 6.2 万栋裁到 1.2 万；`IS_MOBILE` 判定已写好。
- **应对（待做）**：手机实测后按需降级——降 `pixelRatio` 上限（1.5）、A/B 环半径减半、关窗光。三者都已有开关位。

### 风险-4：第三方仓库引用的许可合规

- **风险**：看台地理基准参考了 `hszzhua2/stadium-seat-explorer`（人工核实为 **MIT**，已采纳其基准数据）；Poly Pizza / Poly Haven 素材许可各异。
- **应对（已做）**：LICENSE 注明 OSM 数据 © OpenStreetMap contributors (ODbL)；声明非官方粉丝作品，与两俱乐部无关；3D 素材阶段全部选用 CC0（无需署名）。
- **应对（可选）**：若公开发布宣传素材，在页脚补一行 OSM 署名更稳妥。

### 风险-5：部署链路

- **风险**：Pages 免费版要求公开仓库；Actions 配额（公开仓库免费）；`github.io` 在部分网络环境访问不稳定。
- **应对（已做）**：仓库已公开；工作流只跑 `vite build`（约 30 秒，配额压力极小）；`vite.config.js` 已设 `base: './'` 相对路径，Pages 直接可用。
- **应对（可选）**：国内访问不稳时可镜像到 Cloudflare Pages（导入 Git 仓库即可，零改动）或 WorkBuddy sites 技能发静态托管；要自定义域名则在 Pages 设置里绑定。

### 风险-6：本地凭据

- **风险**：macOS 钥匙串里存有一条**过期的 git 凭据**，shell 端 `git push` 会认证失败。
- **应对（已做）**：推送统一走 GitHub Desktop 图形端（已验证可用）。
- **应对（建议）**：在「钥匙串访问」里搜索 `github.com` 删掉旧条目；或 `git credential-osxkeychain erase` 清理后重新登录。

### 风险-7：彩蛋键盘输入与移动端

- **风险**：数字彩蛋依赖物理键盘，手机端无法触发。
- **应对（可选）**：移动端在 HUD 加两个隐藏按钮（长按标题触发），工作量约 20 行。

## 六、与原方案的偏差及理由

| 偏差 | 理由 |
|---|---|
| 球场生成改为**自写参数化生成器**（原计划移植外部仓库代码） | 原仓库 OT 模块与它自己的材质/UI 深度耦合（25 KB + 48 KB），抽出会破坏方块风一致性；已采纳其地理基准数据，仓库 MIT 合规 |
| 伊蒂哈德长轴朝向**自行补测** | 方案只给了老特拉福德的实测值；本次从 OSM 草坪 way（距球场中心仅 12 m）实测 159.9° |
| 验收方式改为**CDP 截图 + Python 逐像素统计** | 方案的目测验收在实际执行中系统性失真（见 Bug-7），定量验收直接揪出 5 个肉眼不可见的 bug |

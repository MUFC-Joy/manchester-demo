## D-001 · 球场朝向：采用实测值，不采信印象

**日期**：2026-10-15

**结论**：

| 球场 | 草坪长轴方位（从北顺时针） | 来源 |
|---|---|---|
| 老特拉福德 | **70.63°** | hszzhua2/stadium-seat-explorer 的 `OLD_TRAFFORD_GEO_REFERENCE.zBearing = 250.63°`（+Z 指向 Stretford End），折算 70.63° |
| 伊蒂哈德 | **159.9°** | OSM way/136117083（leisure=pitch, sport=soccer, surface=grass, 距球场中心 12 m, 115×85 m）的 PCA 主成分方向 |

**老特拉福德三源互证**：

| 来源 | 长轴方位 |
|---|---|
| stadium-seat-explorer（pitch 基准） | 70.63° |
| Nominatim 球场建筑轮廓 way/99403577 最长直边（115.9 m） | 70.13° |
| 同轮廓 PCA | 73.69° |

前两者差 0.5°，判定可信。**不要**凭印象设成"南北向"。

**公式**：使模型本地 +X 指向方位 θ 的 yaw 为 `π/2 − θ`（推导见 `core/geo.js` 注释）。

**伊蒂哈德的教训**：球场建筑轮廓接近正方形（231 × 242 m），PCA 对正方形不可靠；"最远两点"算法拿到的是**对角线**而不是长轴，两者都会给出错误答案。正确做法是找到**球场草坪**本体，或分析轮廓的**直边方位**。

## D-002 · 球场生成：自写参数化生成器，不移植 stadium-seat-explorer 的 OT 模块

**日期**：2026-10-15

**方案原文**：P3 要求"读 stadium-seat-explorer 源码，抽出其 OT 的生成模块接进我们的材质系统"。

**实际做法**：自写 `src/stadiums/stadium.js` 统一参数化生成器，老特拉福德与伊蒂哈德共用。

**理由**：

1. 该仓库的 OT 模块（`src/old-trafford.js` 25 KB + `src/stadium.js` 48 KB）与其自身的材质系统、座位数据加载、venue-ui 深度耦合，抽取成本高于重写；
2. 抽进来会带入它自己的配色与比例，**破坏本项目的方块风一致性**（方案 §6.4 明确这是"决定成片质感的隐形关卡"）；
3. 两座球场共用一套参数化生成器，风格统一是"白送的"（方案 §3 原话）。

**已采纳该仓库的部分**：地理基准数据 `zBearing = 250.63°`（见 D-001）与"只支持 GLB 导入不支持导出"的结论。

**该仓库已人工核实**：存在、MIT 协议、含 Anfield / Camp Nou / Bernabéu / Allianz / Old Trafford 五座球场。方案的 §2 核查无误。

## D-003 · OSM 数据必须排除 `building=stadium` / `leisure=stadium`

**日期**：2026-10-15

**现象**：程序化球场的座椅海"永远看不见"，改成任何颜色都不显示。

**根因**：老特拉福德的四个看台在 OSM 里是四个独立的 `building=stadium` way（Sir Alex Ferguson Stand / West Stand / East Stand / Sir Bobby Charlton Stand）。分类函数按 `building` 优先级把它们当普通建筑挤出，正好落在球场位置上，**把整个碗形看台盖住**。

**修复**：`classify()` 里在判断 `building` 之前先排除 `building === 'stadium'` 和 `leisure === 'stadium'`。

**影响**：P1 建筑数 233 → 229（减少的 4 个就是四个看台）。

**推广**：做"真实地理 + 程序化地标"这类项目时，凡是程序化生成的地标，都必须在数据管线里把 OSM 对应要素**显式排除**，否则一定会叠两层。

## D-004 · InstancedMesh 必须关闭 frustum culling（本项目的用法下）

**日期**：2026-10-15

**现象**：座椅海（4946 + 4304 个实例）完全不可见，但 `renderer.info.render.triangles` 又包含它们。

**根因**：`InstancedMesh` 默认用**基础几何体**（单个 0.62m 盒子）的包围球做视锥剔除，而实例被分散到几百米外。包围球在原点附近，整个 mesh 被整块剔除。

**修复**：`inst.frustumCulled = false`。

**代价**：每帧都提交全部实例。对本项目可接受（两座球场合计 ~9200 实例 = ~11 万三角形，预算 60 万）。

**若将来要省**：给 InstancedMesh 手动算一个覆盖全部实例的包围球（`boundingSphere` 需要包含平移后的位置），再恢复 culling。

## D-005 · 多边形质心公式：分母必须用有符号面积

**日期**：2026-10-15

**现象**：233 栋建筑里 153 栋被 LOD 分环逻辑丢弃。

**根因**：`centroidAndArea()` 的分母误用无符号面积，导致质心坐标符号和量级都错，环判定（按质心到两球场的距离）全部失真。

**修复**：

```js
a *= 0.5            // 有符号面积
cx /= 6 * a         // 分母用有符号面积
cz /= 6 * a
return { cx, cz, area: Math.abs(a) }
```

**推广**：标准多边形质心公式 `Cx = Σ(x₁+x₂)·cross / (6·A_signed)`，`A_signed` 必须带符号；面积取绝对值只用于面积本身。

## D-006 · 验收不靠看图，靠读像素

**日期**：2026-10-15（源自本会话早些时候 Blender 工作台的经验）

**教训**：3D 场景的预览/截图存在显示增强，"看起来颜色不对"可能是显示层的错觉。本次 Blender 工作台曾因此把"其实已经是深棕色"误判为"还是浅色"，连改三轮材质都没用。

**纪律**：本项目的验收全部量化——

- 配准：两球场距离误差 ≤ 100 m
- 性能：三角形数、draw calls
- 视觉：用脚本解析截图 PNG 的像素，统计目标色（座椅红 / 草坪绿 / 混凝土）的占比

**工具**：Chrome 155 无头 + `--remote-debugging-port` + CDP 轮询页面就绪后 `Page.captureScreenshot`，再用 Python 解析 PNG（`zlib` + 逆滤波 + 逐像素统计）。不依赖任何第三方截图/图像库。

## D-007 · 视口 Rendered 模式 = 出图，所见即所得

**日期**：2026-10-15

Three.js 项目里，视口的 Rendered 模式与最终出图走**同一条渲染管线**（同引擎、同材质、同 HDRI、同曝光）。如果两者看起来不一样，只可能是**相机机位**不同——不同角度看到的面不同（例如双色材质的桌子，俯视是浅色台面，平视是深色侧板）。

排查这类问题先对相机参数，不要怀疑渲染器。

## D-008 · 风格基准 = 参考视频的"白色模型城"，注册表条目必须 fail fast

**日期**：2026-10-15

**背景**：用户反馈首版效果"完全不符合预期"。截帧参考视频（BV1P4pp6YEk4）后确立风格基准并重做视觉层。

**决策一（风格）**：
- 白天 = 亮白建筑模型风：白/米色墙体 + 程序化窗格（世界坐标对齐 6m×3m）、浅色地面、中灰沥青、行道树、渐变天穹 + 云。方案 §6.4 原建议的"灰绿地 + 暖灰楼"色板废弃。
- 夜晚 = 深蓝夜空 + 整楼窗格暖光（62% 亮窗）+ 路灯光池 + 地面压到深灰蓝。原"楼顶发光小方块"窗光方案废弃（nightLights.js 删除）。
- 渲染器启用 ACESFilmicToneMapping：白墙 + 高光照下无色调映射会削平成纯白，ACES 的软滚降就是视频里那种"柔白"。
- 性能红线不放松：新增树/虚线/路灯把三角形推到 696k（超 §6.2 预算 16%），通过道路折线渲染前 DP 简化（road-2 从 175k 砍下来）+ 数量收敛，回到 563k。**超预算砍开销，不放宽预算**。

**决策二（工程）**：昼夜插值注册表（daynight.js registerLerp）里 obj 为 undefined 时会静默把异常推迟到每帧 apply，导致"注册之后的所有系统静默失效"且极难排查（本次天穹/路灯失效 30 分钟）。规则：**registerLerp/registerDome/registerWindows 注册时必须校验 obj 非空并 console.error fail fast**；从 tick 包装里取值一律 `xxx.out.yyy`。
